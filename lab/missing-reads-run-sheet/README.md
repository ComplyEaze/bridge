# Missing reads: raw answers for allocations on vouchers, foreign currency, statutory masters and HSN

Synthetic companies `BRIDGE SHAPE LAB` and `BRIDGE CORPUS FOREX` only, one at a time. **Read only:** nothing is keyed, imported, altered, accepted or deleted, no company feature is changed, no backup is needed, and no voucher screen is opened. Tally's current date is never changed. Every request is a Collection export whose header `<ID>` equals the `NAME` of the collection the request defines, and every `<TYPE>` is one that an earlier committed request already sent (`Company`, `Currency`, `StockItem`, `StockGroup`, `TaxUnit`, `Voucher`).

The answers are the raw bytes a first slice of each read would be built from. Not sent again, because answers already exist: the HSN codes on ledgers and groups of the synthetic book with company number 100033 (its company-level code is not returned by the company request, per the lab results), its GST rate details, tax units and company object, the two foreign-currency vouchers of 15 September 2026, and the foreign-currency ledgers and trial balance (committed captures and lab branches). Not sent because they would need a seeding write, which is a separate sheet: TDS/TCS and a GST classification master (both settings read No in the company-feature captures of the two books of this sheet and in the company object of the book with company number 100033).

**What is new.** The raw answer of the cost-centre allocation voucher; the two-batch Purchase read twice (ledger entries, then inventory entries, a shape never sent before); HSN and GST detail lists on stock items and stock groups; tax units and the Currency master with every native method on books that have none captured. Where a step adds to a committed request, the table "Where each request comes from" names the source and the one change.

Files: `requests/` (14 requests, UTF-16LE with a byte-order mark), `check.py`, `check-request-ids.py`, `SHA256.txt`. First check the files against `SHA256.txt` (PowerShell: `Get-FileHash -Algorithm SHA256 FILE`; or `certutil -hashfile FILE SHA256`). Then run `python check-request-ids.py requests` (or `py -3 check-request-ids.py requests`; use `-I` after the program name where the launcher allows it). EXPECT exit 0 and the line `census: ok 14, skipped 0, FAIL 0`. Below, `check.py` is run the same way.

**Output of `check.py`** is ASCII only: a name outside ASCII (the rupee sign, for example) prints as a `\uXXXX` escape, because the lab console is not UTF-8. (The first version printed the name itself and stopped on the rupee sign at step 11 under the lab console's code page; its self-test had never printed a non-ASCII name.)

**Exit codes of `check.py`.** 0 = PASS: every EXPECT of the step held. 1 = FINDING: an EXPECT did not hold; keep the file, write the printed line down, go on. 3 = STOP. 2 = the check could not run (a missing file, a missing argument, any error): never read it as a pass or as a finding; tell us. Run it as `check.py STEP ANSWER [--census FILE] [--company FILE]`.

**General STOP rule.** Stop and tell us before going on if: Tally shows any dialog, message or warning this list does not name; `check.py` exits 3 or 2; an answer is not a complete envelope with a `COLLECTION`, carries a `LINEERROR`, or has header `STATUS` 0; any answer is above the cap of its step; an answer has not finished after five minutes (do nothing: see "No client time limit"); `GET /status` after a request is not HTTP 200 `TallyPrime Server is Running`. Tally must be at the Gateway with no dialog open before every request. Never press Escape. Press nothing but what a step names.

**How to send.** One request at a time: `curl.exe -s -S -X POST -H "Content-Type: text/xml; charset=utf-16" --data-binary "@requests\FILE" -o ans-STEP.xml -w "%{http_code} %{size_download}" http://127.0.0.1:9001`, each answer written with `-o`, never piped, no client time limit. Note curl's exit code and printed line for every request, then `curl.exe -s -S -o status-STEP.txt -w "%{http_code}" http://127.0.0.1:9001/status`.

**Sizes.** Every cap names the earlier answer it rests on and says whether that answer is the same request on the same book. Where it is not, the step says NEW SHAPE, NEW SIZE or SECOND BOOK, gives a cap and a STOP, and the read is bounded before it is sent by the day's census count (at most 8 vouchers). The kept earlier company-list and book-extent answers of the first book are trimmed to its own row (6,140 and 5,652 bytes as received with three companies loaded; 4,000 and 3,838 as kept). The one-day voucher reads of steps 4 and 6 have no committed answer of their own: these two steps are the first measurement of those days. The nearest figures are: the same request on this book, a whole-year read whose first data part was 1,736,780 B for 42 voucher rows (about 41.4 KB a row); another request on this book (a debit-note and a credit-note day, with extra computed fields), one-voucher answers of 65,002 B and 64,928 B; the same request on another book (a stock lab), 76,868 B for one taxed sales voucher; and the one foreign-currency voucher, 37,190 B. So a voucher answer may hold at most census count x 80,000 bytes and never more than 240,000.

**No client time limit, and why.** A request abandoned in flight can leave the gateway stuck (the lab's wedge rules), so nothing here cancels one. If an answer has not finished after five minutes, do nothing at all: do not cancel it, do not send it again, do not send anything else, and do not touch Tally. Tell us and wait.

**Loading and shutting a company.** Use only Tally's Select Company screen: pick the company from its list and press Enter to load it; to shut a loaded company use the shut action on that same screen. Press nothing else. If more than one company is loaded, or a company loads that the step does not name, or the screen offers any choice this list does not name, STOP and tell us.

**Identity.** The answers of steps 3 to 10 and 17 carry GUIDs, and `check.py` tests each against the book's own GUID from the book-extent answer (a row with no GUID is a STOP). The currency answers may carry none, so `check.py` tests one only if it is present; those answers rest on step 1 or 14 (the book loaded alone) and on the byte-identical book-extent re-reads of steps 13 and 18.
