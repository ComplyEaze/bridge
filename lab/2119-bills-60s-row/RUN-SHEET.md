## What it decides
The build under test sends Tally's Bills Receivable and Bills Payable report requests with a 60-second limit; every other request keeps 20 seconds. On BRIDGE CORPUS DENSE at 31 March 2026, the Receivable request alone took 41.5 s and 36.7 s by curl, and the tool on a 20-second build refused the call on that post (`lab/2119-bills-read-timing-answers`, R4, R5 and T3). The tool sends each report twice with `GET /status` between and after, so an answered call there is expected to take about 85 s (inferred; 70 to 100 s is accepted as expected).

The row decides, for this build:
1. **S1:** whether `outstandings` at 31 March 2026 answers through the lab's stdio client, with its totals equal to R4's, and how long each request was held.
2. **P1:** what a second ComplyEaze Bridge process sees when it calls `tally_status` 10 s into S1.
3. **S2:** whether a read sent straight after S1 (`ledger_masters`) answers.
4. **H1 and D1:** how long this Claude Desktop on Windows waits for one tool call, by the repository's sleep server with no Tally request (H1), and whether it waits for the whole `outstandings` call (D1). The repository's only measurement of a Desktop limit is on macOS (protocol reference §11f: silent calls up to 130 s answered, a 250 s call cut at 240 s; PARTIAL); the Windows row of `docs/agent/mcp-host-call-timeouts.md` is empty.

**The limit is held** (the release does not ship it as is; the run coordinator decides what follows) if any of these is so:
- **(a) S1 is refused** with cause `native_bills_report_deadline_exceeded`: the coverage the limit was accepted on did not hold on this book.
- **(b) S1 does not answer:** refused with any other cause, or a STOP before its answer. The row is then incomplete, and the run coordinator decides.
- **(c) S1 or D1 answers with totals that differ from R4's** (`open_bills_total` other than 29,900, R4's `BILLFIXED`; `receivable` other than 1,425,845,144.50, the size of R4's `BILLCL` sum, its sign ignored; or `payable` other than 0), read from the answer's `result` fields, which the stdio client's truncation flag does not cut: a wrong answer is worse than a refusal.
- **(d) Desktop gives D1 up.** Decided once Desktop has ended the call (a cancellation, a timeout or an error shown), from Desktop's MCP log by the `outstandings` call's JSON-RPC id, once its `tools/call` line is found there: no result for that id, or a cancellation for it, is a give-up, whatever Desktop showed. Desktop showing a timeout, a cancellation, or an error that names a time limit is a give-up too, even if a result for that id reaches the log later.
- **(f) D1 ends any other way than with the tool's own whole result** in Desktop's MCP log: refused with cause `native_bills_report_deadline_exceeded` = the limit is held, as (a); refused with any other cause, or a result Desktop did not show (for example an error about its size) = the row is incomplete, and the run coordinator decides.
- **(e) Desktop's limit is not shown to be at least 90 seconds.** Any one of these shows it:
  - an H1 sleep call answered whole with `seconds` 130 in its `received` arguments;
  - the same with `seconds` 90;
  - D1 answered whole, with at least 90 s between its `tools/call` and its result in Desktop's MCP log.

  "Answered whole" means Desktop showed the tool's own result (for a sleep call, the text `slept 130.x s` or `slept 90.x s`), and Desktop's MCP log holds that result. A `result_sent` in the sleep server's log alone does not count. A call whose `received` arguments differ from the ones asked for shows nothing. With H1 skipped or not shown, and D1 answered in under 90 s, (e) holds the limit.

**D1 not decided.** D1 skipped (rule 11), with no answer from Desktop in 10 minutes, any STOP during D1, or no `tools/call` line for its `outstandings` in Desktop's MCP log (or a log that cannot be read) leaves (d) and (f) undecided: the row is incomplete, and the run coordinator decides.

**P1 and S2.** They decide no hold. A B that answered instead of being refused busy, or an S2 refused, goes to the run coordinator with the row, because the change's own text says another process is refused busy while a Bills request runs.

**The call budget** (owner's rule, separate from the hold). A call is cut by Desktop when Desktop showed a timeout or a cancellation for it, or when the sleep log shows `cancelled` for it, or a `stdin_closed`, `signal` or `stdout_error` event with `running` above 0 (the repository's signs of a host ending a call). Take the shortest time, from the `tools/call` to the cut in Desktop's MCP log, among the cut calls of H1 (with their `received` `seconds` as asked) and D1. If it is under 130 s, the row shows Desktop's limit is under that time; for the budget, anything under 130 s is taken as under about 120 s. A call-level budget for the two Bills reads, refused in-band before a post that would pass it, is then built, and this row is run again on that build before the change merges. No cut call decides nothing about the budget: record why (H1 not run, arguments changed, an approval lapsed, an entry not loaded, or an error that names no timeout or cancellation with none of those events).

It decides nothing about other books, other dates or Gold.
