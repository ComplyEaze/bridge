Record the MCP client that sends the calls and its per-call timeout: the tool keeps each call under about 45 seconds and assumes a host timeout of about 60; a call the host cancels loses its reply (`import_dispatch_outcome_unknown`), which is counted apart from a refused read-back.

**Timeouts.** The built tool has its own 20-second deadline for each request it sends and abandons a request that passes it (the request keeps running in Tally). The verification read before a post splits a part that passes the deadline and sends the halves within the same call, so a call can succeed while a request it gave up on is still running in Tally. After EVERY call, read `egress_log` and the call's evidence: any `request_deadline_exceeded`, size refusal or refused part BEFORE the post was sent (the result's attempt is not recorded: `attempt_recorded` false) is a STOP: nothing more is sent, no key is pressed, the screen is photographed, and the answers are reported whole. The same AFTER the post was sent (the attempt recorded) is recorded beside the refusal count, not a STOP. `voucher_window_volume_unestimated` (a census that timed out or was too large; see its `cause`) before a send is a STOP. Any call with no answer within 10 minutes, and any dialog on Tally's screen, is a STOP. A refusal of the read-back AFTER a post was sent is what this item counts (see step 3).
