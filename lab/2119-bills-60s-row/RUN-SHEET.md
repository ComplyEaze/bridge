## What it decides
The build under test sends Tally's Bills Receivable and Bills Payable report requests with a 60-second limit; every other request keeps 20 seconds. On BRIDGE CORPUS DENSE at 31 March 2026, the Receivable request alone took 41.5 s and 36.7 s by curl, and the tool on a 20-second build refused the call on that post (`lab/2119-bills-read-timing-answers`, R4, R5 and T3). The tool sends each report twice with `GET /status` between and after, so an answered call there is expected to take about 85 s.

The row decides, for this build:
1. **S1:** whether `outstandings` at 31 March 2026 answers through the lab's stdio client, with its totals equal to R4's, and how long each request was held.
2. **P1:** what a second ComplyEaze Bridge process sees when it calls `tally_status` 10 s into S1.
3. **S2:** whether a read sent straight after S1 (`ledger_masters`) answers.
4. **H1 and D1:** how long this Claude Desktop on Windows waits for one tool call, by the repository's sleep server with no Tally request (H1), and whether it waits for the whole `outstandings` call (D1). The repository's only measurement of a Desktop limit is on macOS (protocol reference §11f: silent calls up to 130 s answered, a 250 s call cut at 240 s; PARTIAL); the Windows row of `docs/agent/mcp-host-call-timeouts.md` is empty.

**The limit is held** (the release does not ship it as is; the run coordinator decides what follows) if any of these is so:
- **(a) S1 is refused** with cause `native_bills_report_deadline_exceeded`: the coverage the limit was accepted on did not hold on this book.
- **(b) S1 does not answer:** refused with any other cause, or a STOP before its answer. The row is then incomplete, and the run coordinator decides.
- **(c) S1 answers with totals that differ from R4's** (`open_bills_total` other than R4's `BILLFIXED`, or `receivable` other than the size of R4's `BILLCL` sum): a wrong answer is worse than a refusal.
- **(d) Desktop gives D1 up.** An error whose text names a timeout or a cancellation is a give-up whatever its time. Any other error is a give-up unless D1's `response_prepared` record is earlier than the error. The record is read from the result of step 6's `egress_log` call, as Desktop's MCP log holds it (not from the chat text). Both times are compared in UTC. A missing record counts as a give-up.
- **(e) Desktop's limit is not shown to be at least 90 seconds.** Any one of these shows it:
  - an H1 sleep call answered whole with `seconds` 130 in its `received` arguments;
  - the same with `seconds` 90;
  - D1 answered whole, with at least 90 s between its `tools/call` and its result in Desktop's MCP log.

  "Answered whole" means Desktop showed the tool's own result (for a sleep call, the text `slept 130.x s` or `slept 90.x s`), and Desktop's MCP log holds that result. A `result_sent` in the sleep server's log alone does not count. A call whose `received` arguments differ from the ones asked for shows nothing. With H1 skipped or not shown, and D1 answered in under 90 s, (e) holds the limit.

**D1 not decided.** D1 skipped (rule 11), or with no answer from Desktop in 10 minutes (a STOP), leaves (d) undecided: the row is incomplete, and the run coordinator decides.

**The call budget** (owner's rule, separate from the hold). H1 shows Desktop's limit under 130 s when the 130 s call, with `seconds` 130 in its `received` arguments, was cut by Desktop: Desktop showed a timeout or a cancellation, or the sleep log shows a `cancelled` event for it. The run coordinator then treats the limit as under about 120 s. A call-level budget for the two Bills reads, refused in-band before a post that would pass it, is built, and this row is run again on that build before the change merges. Any other H1 outcome decides nothing about the budget: record why. That covers H1 not run, arguments changed, an approval lapsed, the entry not loaded, or the call failing with an error that names no timeout or cancellation and has no `cancelled` event.

It decides nothing about other books, other dates or Gold.
