- The party/ledger master workbook now shows the mailing details for a book with many master alterations but few ledgers. For a book whose master-alteration mark is past 4,266, Bridge already counts the ledgers before reading them. Where the counted ledgers fit the read's estimated bound, each allowed four further mailing entries the mark may not show (one save in Tally can add several) and one more for each alteration beyond them, the workbook now asks for the mailing details instead of leaving those columns not observed. This is an allowance (unverified), not a bound: it rests on one lab book. Such a book, with a mark from 4,267 to about 13,300 and up to about 1,265 ledgers, used to be read without the mailing details and is now sent the larger request; if a party holds more mailing entries than allowed, the read can run out of time or past its size limit. The export then reads the book once more with the standard request, and writes the workbook without the mailing details, with a note in its header that the larger read failed (#2214). Where the larger read was cut while Tally may still be working on it, the export first waits for Tally to finish, for about a minute at most, sending only status checks; the app's other reads of that Tally wait behind it meanwhile. **A book that exported before can still fail** where the larger read's answer broke off, or where Tally was still working after that minute; the error then says the mailing addresses were part of the failed read. A book of more ledgers, or with more alterations than fit, is read as before. A book whose mark is from 3,201 to 4,266 is not counted, so it is still read without them (part of #2074).
