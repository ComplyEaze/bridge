## Reading start-up information (Q2)

`startinfo.ps1` loads `startinfo.cs` with `Add-Type` (Windows PowerShell 5.1, nothing installed) and reads a running process's own parameters block (`RTL_USER_PROCESS_PARAMETERS`, through the PEB), where Windows keeps what the process was started with:

- `window_flags`: the STARTUPINFO `dwFlags`, named bit by bit (`USESHOWWINDOW`, `USESTDHANDLES`, ...);
- `show_window_flags`: `wShowWindow`, with its `SW_` name, and whether it is used for the first show (only when `USESHOWWINDOW` is set);
- the starting position, size and title fields; `console_handle`, `console_flags` and the three standard handles; the image path and command line;
- the image's PE subsystem (2 GUI, 3 console) and the parent pid, checked against pid reuse by creation time.

Every read prints one RESULT line: `OK`, or `OPEN_FAILED` (87 the pid is not running, 5 access denied), `QUERY_FAILED`, `READ_FAILED`, `PARTIAL_READ`, `WOW64_TARGET`, `HOST_NOT_64BIT`, `LAYOUT_CHECK_FAILED` (the block's image path differs from the one Windows reports for the process, after the normalising below, so the offsets are wrong on this Windows), or `PARENT_UNREADABLE`. The image check compares the two paths after setting aside the slash direction, the case and a `\\?\` or `\??\` prefix, because `client.py` starts the exe by a forward-slash path. A failed window listing prints `WINDOWS_ENUM_FAILED` and exits 2; a failure of the script itself prints one `STARTINFO_FAILED` line and exits 2; exit 1 means only a wrong self-test case. Its self-test (step 0) proves the offsets on the lab's own Windows: twelve parse cases on synthetic blocks; its own process against `GetStartupInfoW` and `GetCommandLineW`; then three `ping.exe` children it starts with known values, the third as Python starts the server (no application name, a command line beginning with the exe's path in forward slashes), each read and left to exit by itself.

**What cannot be read this way, and is not claimed.** The creation flags given to `CreateProcess` (for example `CREATE_NO_WINDOW`, `DETACHED_PROCESS`, `CREATE_NEW_CONSOLE`) are not stored where a reader can reach them after the start; only their effects are, which this row reads: the console handle in the block and, by `-Mode console`, whether the process has a console and whether that console has a window. The `console_handle` value read after the start is the console connection the process holds, not the marker its parent passed. The helper's error output is not readable on this path (above). What Windows did with `wShowWindow` at the first show is inferred from the box reads, not read.

Chain reads (`-Mode chain`) print the server and its parent in full; for higher ancestors (the shells and the operator's tools) they print only the image's file name and the lengths of the command line, folder and title, because those texts may hold user paths or session values.

## Bounded output

`boxstate.ps1` prints one line per window of one process. `startinfo.ps1` caps the command line at 300 characters, paths at 260, titles at 120 (a window title at 60), lists at most 20 windows per process with the count omitted, and at most 6 ancestors. `boxwatch.ps1` writes one log line per event and per read, never per poll, so `cat reads-<X>/<X>-watch.txt` reads a bounded file; `client.py` writes one `client-log.txt` line per event and per call, so `cat run-<X>/client-log.txt` does too. `ops.ps1` lists at most 200 files and caps an error message at 200 characters. `exes.ps1` prints at most 40 files and 5 errors, each with the count omitted. `ans.py` prints at most 10 companies. `count8.py`, `run.py` and `client.py` keep their previous bounds. ## Decides

One book, one release, one Windows account, one sitting: every reading is **partial** at best, and one box per launch is one sample.

- **`M0` and its lag.** `M0 (lag_s N)` says the box was minimised at the first read, N seconds after the helper's creation, with no screen act before it. It is read as "opened minimised" only together with N: up to 10 s it means opened minimised or minimised within those seconds with nothing acting on the screen (the two are not told apart); above 10 s it says nothing about how the box first showed, only that it was minimised before any screen act, as `MB` does.
- **L1 `M0`:** the old build's box was minimised on the 19/20 Nov path with no screen act before it (read with its lag, above): the failure is the program's or its launch's, seen without the screen tool. Q2's reads then show what show state the helper had (`show_window_flags` with `USESHOWWINDOW`, or none). **L1 `M1`:** the box opened normally and was minimised across one screenshot by the screen tool: the boxes of 19 and 20 Nov are explained by the act of looking, not by the build's launch (partial: one sample; consistent with the #2161 record's finding 5). **L1 `MB` or `M3`:** minimised without the screenshot as its last act before; recorded as it stands, the cause not shown. **L1 `N`:** the failure was not reproduced on its own path; its cause stays not shown, and the grant and the screenshot are not shown to cause it in this sitting.
- **L1 not run:** Q1 on the 19/20 Nov path is not answered by this row. L0 alone answers it only for the granted path (`exe-old`), and says nothing about the path of 19 and 20 Nov.
- **L0 `N` beside L1 `M1`:** the grant decides whether the screenshot minimises the box (partial). **L0 `N` beside L1 `M0`:** the path or its grant changes how the box first shows; the build's bytes are the same, so this points to the screen tool's handling of an app outside its grant, not to the exe. **L0 equal to L1:** the grant is not the variable here. **L0 `M1`:** the screenshot minimises even a granted box; that contradicts the #2161 record's reading and is reported.
- **Q2, on every launch read:** the `window_flags` and `show_window_flags` the helper and server hold are **verified** for this sitting once the self-test passed. `USESHOWWINDOW` clear on the helper means the helper was given no show state; a minimised box then did not come from its STARTUPINFO. `USESHOWWINDOW` set with a minimising `SW_` value names the show state it was given. L1 and L0 equal in these fields means the path change did not change what the processes received. The console line says whether the server has a console and whether that console has a window; creation flags themselves are not read.
- **L2, after its pair's `M0`:** `iconic=False` at R1 means the fix restored a box that was minimised when it was activated on this path (partial; the restore line cannot be read here). `iconic=True` at R1 means it did not; as the code reads, an OLD box minimised at its activation would have closed itself (`closed-<read>`, `import_review_too_large`), so the OLD `M0` box was more likely minimised after its activation (inference), and NEW's `iconic=True` is then the fix's limit on this path (a box minimised after its activation stays minimised: #2569's FAIL here), not a restore that misfired. **L2, after its pair's `M1` or `MB`:** `iconic=True` at R2 means the fix does not cover a box minimised after its activation, as its code reads; `iconic=False` at R2 means something activated the box again or the screenshot did not minimise it this time; the two are not told apart. **L2 not run:** Q3 is answered from the code only (unverified live).

- **A `failed-<read>` word:** the reads before the failed one stand (each was `iconic=False`); nothing is read after it; it is not `N`.
