- The party/ledger master workbook now shows the mailing details for a book with many master alterations but few ledgers. For a book whose master-alteration mark is past 4,266, ComplyEaze Bridge already counts the ledgers before reading them. Where the counted ledgers fit the read's estimated bound, each allowed four further mailing entries the mark may not show (one save in Tally can add several) and one more for each alteration beyond them, the workbook now asks for the mailing details instead of leaving those columns not observed. This is an allowance (unverified), not a bound: it rests on one lab book. Such a book, with a mark from 4,267 to about 13,300 and up to about 1,265 ledgers, used to be read without the mailing details and is now sent the larger request; if a party holds more mailing entries than allowed, the read can run out of time or past its size limit. Where Tally answers past the size limit and says so at the start of its answer, or where its answer comes back but breaks off or cannot be read, the export reads the book once more with the standard request, and writes the workbook without the mailing details, with a note in its header that the larger read failed and why (#2214). This fallback has not been run against Tally: only Tally's answer past the size limit, and a separate read straight after it, were seen in the lab. **A book that exported before can still fail** only where the larger read runs out of time, since Tally may still be working on it; the export then fails, and its error says the mailing addresses were part of the failed read, without saying the size estimate was too low. A book of more ledgers, or with more alterations than fit, is read as before. A book whose mark is from 3,201 to 4,266 is not counted, so it is still read without them (part of #2074).
