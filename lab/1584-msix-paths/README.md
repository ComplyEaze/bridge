Not for merge. Reads of Tally only: no post, no ledger create, no import into Tally. `build_import_xml` writes an import FILE on this PC and reads Tally; nothing is sent to Tally's import. One synthetic company, loaded alone. **No download and no install:** the build is the published 0.7.0 `bridge_mcp.exe` the lab already holds from `lab/0.7.0-post-publish`. No owner act is needed; nothing here quits, restarts or reconfigures Claude Desktop. About 90 minutes.

Marks: V = read at a named source; U = not measured. Every outcome below is recorded as found, never explained away.

## What it decides

1. **Which side of the package boundary each process is on.** Two separate readings, never one inferred from the other: the process's package family (`GetCurrentPackageFamilyName`, read by `probe.ps1` for each shell and by `client.py` for itself and for the `bridge_mcp.exe` it starts), and where a NEW file it writes under `%LOCALAPPDATA%` lands (K1). A package can have identity with write redirection off, so the two can disagree; both are recorded. Never decided by whether one side can read a file (inside, AppData reads merge: a packaged process sees the real file too). U, from the run coordinator's brief: on 30 Oct a silent installer run from the lab session landed in Claude Desktop's virtualized AppData.
2. **What Windows reports, inside the package, for a file the package redirected** (K1): the final path in three forms (the one `std::fs::canonicalize` asks for, the opened name, the NT form), and the known folders Bridge resolves with and without the redirection flags. This decides whether #1569's shown path can work and which API a fix would use.
3. **#1459: where a built import file lands and what `build_import_xml` prints for it**, for a process inside the package (I rows), one outside it (O rows) and, if the lab session can call them without a prompt, the installed extension's tools (E rows). Since #1569 (0.6.0) the result carries `result.path` from `user_visible_path` and a `result.path_state` of `resolved`, `as_is` or `unresolved` (V: `src-tauri/src/agent_import.rs:1749`; `src-tauri/src/local_files/visible_path.rs:49-55` (the state words), `:72-85` (the function)). What it printed on a Store install has never been recorded (V: #1459, last comment).
4. **#1459 step 5, never run:** what `bridge_mcp --local-data-report --show-paths` prints from each side, and which folder it counts. The command prints logical paths only (V: `src-tauri/src/agent_import_local_data.rs:540-549`) and needs no Terms and no Tally (V: `src-tauri/src/agent.rs:3799-3811`, `src-tauri/src/agent_import_local_data.rs:571-583`). Also: which journal (`R` or `Q`, below) an in process appends to, and how many lock files each leases folder holds (#1459's open 1,403-lock row, counts only).
5. **#1584 / #1641: the port locks.** Since 0.6.0 each lock is a set: one file under `<LocalAppData>\Bridge\agent\native-dispatch-leases` and one under `%USERPROFILE%\.complyeaze-bridge\coordination\native-dispatch-leases`, taken in that order, all or none (V: `src-tauri/src/local_files/paths.rs:52-77`, `src-tauri/src/local_files/lock_set.rs:48-79`). Whether the profile file is one file for both sides (L), and whether a hold on one side refuses a send from the other (C rows), was never run on a Store install (V: #1584, last comment).

## Names used below

- `LA` = `%LOCALAPPDATA%`, `UP` = `%USERPROFILE%`, `F` = the Claude package family name read at 0c.
- `R` = `LA\Bridge\agent` (the real data folder); `Q` = `LA\Packages\F\LocalCache\Local\Bridge\agent` (the package's private copy); `P` = `UP\.complyeaze-bridge\coordination` (the profile lock root). `R-leases` etc. = their `native-dispatch-leases` subfolders. `probe.ps1` opens the nine `K.lock`, `K.snapshot.lock` and `K.wire.lock` files by name in each, and counts every leases folder by suffix.
- **in** = the lab session's own shell, or a process it starts. **out** = a process started from the Win+R box (owned by Explorer). Which side each really is on is decided at K1 and by the package-family readings, not assumed.
- **Every command of a step** goes into `C:\bridge-lab\1584\run\<step>-<side>.cmd`, written as ASCII (`[IO.File]::WriteAllText(path, text, [Text.Encoding]::ASCII)`; never PowerShell's `>` or `Out-File`, which write UTF-16 that `cmd` cannot run), its text recorded in `notes.txt`. A probe or report line ends with `> C:\bridge-lab\1584\evidence\<step>-<side>.out 2>&1` unless it names its own output files, and the last line of every `.cmd` is `echo %ERRORLEVEL% > C:\bridge-lab\1584\evidence\<step>-<side>.exit`. An in step runs it from the lab's PowerShell as `cmd /c <that path>` (from a bash shell: `cmd //c`).
- **An out step** is always: the lab writes the `.cmd` as above; opens the Run box (Win+R); takes a screenshot that shows the Run box focused (no screenshot, or another window focused = do not type; try once more, then the WMI method); types the `.cmd`'s full path and presses Enter. If the lab cannot drive Win+R, it starts the same `.cmd` with `Invoke-CimMethod -ClassName Win32_Process -MethodName Create -Arguments @{CommandLine='cmd.exe /c <that path>'}` and records that; K1 decides whether that method is outside. Every out step uses the method K1 passed. Win+R adds each line to the Run box's history: recorded, not cleared.
- **Requests and settings files** the lab writes for `client.py` are UTF-8 without a BOM, written to `<name>.tmp` and then renamed to `<name>.json`, so the client never reads a half-written file.

## Rules

- One Tally (port 9001), one request at a time; a call in flight is never cancelled or repeated. A tool answer that is not the EXPECT line is recorded and the row ends; no row is retried except where it says so.
- Tools sent: `tools/list`, `tally_status`, `list_companies`, `ledger_masters`, `build_import_xml`, `local_data_report`. Never `post_import`, `verify_import`, `acknowledge_post_review`, a master write, or a raw request to port 9001.
- **Delete nothing.** Built import files, journal lines and probe files stay where they land (they are the evidence); no lock file is removed; each holder has its own stop file. Claude Desktop is never quit, restarted or reconfigured; its settings file is never read or written. No uninstall, no reset or repair of the Store package.
- **What this item leaves behind, permanently, and is never posted:** in `R` and/or `Q` (wherever they land): two or three built single-voucher batch files (`lab1584-i1`, `lab1584-o1`, and `lab1584-e2` if E runs), their journal lines as built-not-posted batches, Terms-record lines and receipt-log lines; probe files under `LA\bridge-lab-1584` (or its package copy); lock files; and `P` if it did not exist (#1584: "the profile folder created from inside the package" is then this item's I1). Each is listed in `kept-local.txt`. No later sheet may post these batches.
- Existence is decided by `probe.ps1` (opening the path: absent, or a Win32 error), never by `Test-Path`. Every command's exit code and output are recorded; an error is reported as an error, never as "absent".
- Order matters (Windows redirects only NEW files, so who creates a file first decides where it is): run the steps in the order written. Every in row comes before every out row that creates the same file.
- STOP = record, change nothing more, send the evidence so far to the run coordinator.
