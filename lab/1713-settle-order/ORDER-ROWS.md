# ORDER-ROWS (#1713, #2176): does a read answered after an abandoned ledger create always see that create, on the connection patterns ComplyEaze Bridge may use?

Not for merge. `LAB-COMMON.md` (v3, the byte copy in this folder, sha256 in `SHA256.txt`) applies in full; where this sheet and it differ, the stricter holds, except the deliberate differences listed below. Steps marked [OPERATOR] are the lab PC operator's. This sheet WRITES: one ledger per row (names below, each used once) into the synthetic company of `lab/1713-abandoned-ledger-create`, and its optional last row ends a Tally process (bounded below).

**WHY.** A ledger create that Bridge stopped waiting for (its 20 s request limit) leaves the batch open and the name held. Today a later reconcile releases the name as `confirmed_absent` when the paired index read finds it absent and the master mark unmoved (#2176), and #1713 proposes to release it also after another master change moved the mark. Both are safe only if Tally always serves a read sent after the create's send ended after the create has run. The earlier sheet (`lab/1713-abandoned-ledger-create`, rows L1 to L5) saw that order on NEW connections only: curl opened a new connection for every send. Bridge builds one HTTP client per session with no pool limits and Tally answers `Connection: keep-alive`, so a create may ride a connection that already served a request while its later read uses another. Whether the pool ever holds two idle connections at once is NOT established here (it is read from code, not measured); K2 and K3 therefore test possibilities, and a PASS for them is not a claim that Bridge produces them. This sheet decides only whether the order rule may be cited for each pattern.

## What is used (every file is checked against its sha256 before the run starts; `order.py` refuses a mismatch)
- THE COMPANY: the synthetic company of the earlier sheet (Silver, TallyPrime 7.2, one currency) with a book large enough that the busy read A lasts at least 120 s (the row note records the measured duration). Never any company other than THE COMPANY. If it no longer exists, every row is void until the row note names one.
- From the earlier sheet's branch (head in the row note): `requests/busy-year.xml` (A), `requests/ledgers.xml` (C), `requests/marks.xml`, and `requests/l2-create.xml` as the template of every create B: the same bytes with only the ledger name changed.
- `order.py` in this folder: `python -I order.py plan.json OUTDIR`. It refuses a non-empty OUTDIR, any file whose sha256 differs, and a named connection used by other than one step. It opens and WARMS every named connection first (one harmless read, answered in full with status 200; otherwise it ends with nothing else sent), takes T0 as the moment the last warm was answered, then sends each step at its time, on a fresh connection or on its named one (checked alive just before; a connection the peer closed ends the step as `stale`). It writes the request in one send, gives up after `limit` seconds counted from just before the send by closing the socket after all bytes were written (`abandoned`), streams answers to files with a running sha256, logs `first_byte`, `written`, `reused` (with the connection's idle seconds) and exactly one `end` per step, classifies the end (answered, bad_status, abandoned, timeout_bound, refused, stale, closed_before_headers, no_content_length, bad_header, short, over_bound, stopped, error:name), writes `done` only when every step has an end, leaves `<name>.sent` before a write step's send and refuses to send it again, and stops all sending when a file `STOP` appears in OUTDIR. Times are seconds since T0 with the UTC clock on every line. It was exercised against a local stand-in that serves one request at a time (a warmed connection reused, an abandoned send, a queued read answered with the busy one, a closed port logged `refused`, a non-empty OUTDIR refused); it has not run against Tally. Its request headers are the set of the earlier curl line plus keep-alive, not claimed equal to Bridge's byte for byte.
- The earlier sheet's `read.py` reads A's answers by structure; C and the observation reads are read for the probe's presence by structure (C4), never by a text search.

## Deliberate differences from LAB-COMMON (each one stated, nothing else differs)
1. Overlapping requests in the timed rows: A, B and C overlap, which is the point. Everywhere else one request at a time.
2. B has a 20 s client limit (Bridge's `DEFAULT_REQUEST_TIMEOUT`), so an abandoned B is a result, not a failure (C3's status, empty-body and size checks do not apply to it). A's bound is 400,000,000 bytes.
3. The optional last row ends a Tally process, bounded in its own section (a widening of C2, authorised by the owner's word of 28 Oct 2026 that the run coordinator records in the row note).
4. Dialogs: while `order.py` runs, [OPERATOR] screenshots Tally's whole window at least every 30 s. A dialog or half-entered screen: create the empty file `STOP` in OUTDIR at once, press no key, copy the text, report (C7); the row is VOID. C3's screenshot after every write is satisfied by this cadence plus a screenshot, `GET /status`, MARKS and LEDGERS before the next row starts.
5. Row R0 is sent by the named build's own tools, not by C3's curl line; Bridge sends its own reads (company list, marks, ledger and group indexes) around the create, and its own 20 s limit applies. The stricter rules of C3 that can still hold do: the create is sent once, never again.
6. Observation reads and C retries are sent by a second plan per read that [OPERATOR] starts at the stated minute; they are reads only, so C3's one-at-a-time rule is relaxed for them exactly as in the earlier sheet's difference 6.

Observation reads (LEDGERS and MARKS) at C answered + 1, + 5, + 15 and + 30 minutes after every compared row, each a separate plan that [OPERATOR] starts at that minute. After an abandoned send Tally may refuse connections for several minutes (the reference measured nine minutes after an abandoned read); a refused read is a result and is re-sent every 30 s until D + 10 minutes.

**What counts.** A row counts only if `order.py` logged `written` for B, an `end` abandoned for B (in L1B-repeat: an `end` answered for B), `written` for C before A's `first_byte`, and C's `first_byte` after A's `first_byte`. A row is VOID, recorded and repeated, if B is answered within its limit or has no `written`, if C is written only after A's first byte (VOID-late, including every C that was refused and re-sent), if any end of B or C is stale, closed_before_headers, short, no_content_length, bad_header, over_bound, bad_status or error, or if D is under 55 s. A dialog or `stopped` is VOID and reported at once.
**PASS-present** (the create ran): the probe ledger is present in C and in every observation read. **PASS-dropped** (the create was lost): absent in C and in every observation read and the master mark unmoved from the MARKS before B. **FAIL**: absent in C and present in any later read, or C answered before A's first byte, or a probe ledger present twice, or a ledger no row created. One FAIL ends the use of the order rule for that pattern: the release rules of #1713 and #2176 must not rest on it for that pattern. The rule is cited for a pattern only when BOTH repeats pass (K0, K1, K2, K3). N1 and L1B-repeat are single rows, partial by the reference's convention.
**Confidence.** One observation per pattern per repeat, on one book, Silver 7.2, ledger creates only. Gold, other releases and other master types stay uncovered, and any text that cites the rule says so.
