# 2027 GST and note fields capture (#2027): Place of Supply, the party's state and registration type, the original invoice number and date of a note, the reason for a note and the supplier's or buyer's note details, keyed with synthetic values on the notes book, and read with the committed native request and with the same request asking for the lists it leaves unexpanded

Not for merge. About 2 hours. This sheet WRITES four vouchers by hand on Tally's screens, then restores the book from a backup; ComplyEaze Bridge only reads. `SHA256.txt` lists every file here with its bytes; check it before step 0.

## What it decides
A lab reading of hand-keyed Sales, Purchase, Credit Note and Debit Note vouchers (`lab/691-w3-answers`) found that every field `vouchers` returns matches Tally's screens, but that several fields a CA checks in GST review are not returned: Place of Supply, the party's State and GST registration type on the voucher, the original invoice number and date of a note, the reason for issuing a note, the buyer's or supplier's note number and date. #2027 lists, per field, whether a committed raw Tally answer carries it and whether the request `vouchers` sends asks for it. In the committed native answer of the 628-C0b row, Place of Supply, the state and the registration type are top-level elements, and the original invoice number and date are empty elements; every voucher-level list that request did not name (among them `ORIGINVOICEDETAILS.LIST`), apart from `OLDAUDITENTRYIDS.LIST` and `PFTDLVERSIONINFO.LIST`, came back as an empty placeholder (why is unverified: that the native request's `*` does not expand those lists is what the second read tests). So this sheet makes two native reads of the same vouchers: the committed one, and the same request with one `NATIVEMETHOD` line added for each of fifteen voucher-level lists that Tally itself named in that answer. It keys the original invoice numbers and dates, the reasons, the note numbers and dates and the supplier invoice with synthetic values that differ from every other typed value, so that each such element can be matched to what was typed; Place of Supply, the party's state and the registration type are not keyed (they take the party's values, which equal the company's) and are attributed by element name only, PARTIAL. A typed value found anywhere in either answer is found, with its path. A list that holds no child element on any of the four vouchers in the second read is "not expanded or empty: undetermined", never "not found". It decides no request, field name or tool change.

## What the row records, and what it does not
For each field of #2027's table: whether Tally lets a value be keyed, the element and path that stores it in the native answers (or that none was found / the lists were not expanded), whether the shipped `vouchers` request returns that element, and the voucher's pre-accept screen text beside it. It decides no field name, request change or tool output. **Confidence:** one voucher per kind, PARTIAL until repeated. Not covered: e-invoice details (#1378), a foreign-currency voucher, a Place of Supply different from the party's state (which would need an IGST ledger the book lacks), an item invoice, TallyPrime 7.1, and the values a real CA would key.
